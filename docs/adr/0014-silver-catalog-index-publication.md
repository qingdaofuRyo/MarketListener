# ADR-0014：Silver Catalog 证据门与查询索引差集恢复

状态：R4-Q-50 实施中；真实 schema5 全量索引已核验，实盘差集恢复待验收。

## 背景

Silver Parquet 是可按分区原子替换的正式行情文件，Catalog 记录分区路径、SHA、行数和 COMPLETE 状态。K 线索引只存路径与时间范围；旧索引若指向已替换的文件，不能视为旧数据快照。本机有约 4.8 亿根 K 线，完整重建约需数分钟。单次通达信盘后导入可改写超过 2,048 个分区，使有界修订流水不足以证明从旧索引到当前的完整变化集合。

## 决定

- Silver 写者在替换文件前推进修订并登记待完成状态，Catalog 与文件提交或安全回滚后才结清。查询在读取 Parquet 后再次核对修订；发生变化时拒绝返回及缓存结果。
- 全量索引只读入通过 Catalog COMPLETE 路径、SHA 和 Parquet 行组数审计的确切文件集合。提交时复核来源修订、Catalog 摘要和索引总行数。
- 索引保存所审计的规范分区路径、SHA、行数清单；修订状态保存单调的 `unknownEpoch`。流水完整时使用确切文件链，流水截断时只有 epoch 与索引基线一致、Catalog 和实体路径集合一致、分区差集有界且每个变更文件重新核验时才增量恢复。超过限制或出现 UNKNOWN、损坏、证据冲突时保持 STALE 并走受审计全量重建。
- 已存在的损坏修订文件不得自动覆盖并重置 epoch。读取报告无效、写入停止；遗失状态重新引导或旧状态审计采纳时使用新的随机 epoch。schema5 索引就绪同时要求完整修订流水合法、待完成写入为空，以及索引 epoch 与当前 epoch 相等。
- 精确认定的旧 schema1 修订只在服务启动迁移或显式索引维护时改写为新修订，记录 UNKNOWN 并赋新随机 epoch；任何旧索引随之失效，只有完整 Catalog/实体 SHA 与行数审计后才能发布新索引。普通 GET 不迁移旧状态，包含额外未知字段或损坏的旧文件保持原样待核查。
- 更新任务排队或运行时不由产品 GET 发起大型重建。任务结束后由发布监测器触发恢复；已发布旧名单可以标 `STALE` 展示，K 线读取待索引同版后恢复。
- 重建失败按相同修订有界退避，修订变化后重新尝试；后台进度只报告阶段、计数和固定失败类别，不暴露来源路径或异常原文。
- 单个死写者的遗留待完成记录只有在 Catalog 与实体 SHA 能证明提交、未替换或被后续同路径提交覆盖时才自动结清。多文件 UNKNOWN 和 Catalog 冲突保留人工核对状态。

## 替代方案

无限扩大 JSON 修订流水会使每次分区写入重写越来越大的状态文件。每次 GET 扫描全部 Parquet 与 Catalog 无法满足页面延迟预算。直接把源修订号写到旧索引，会把尚未纳入的文件误报为 CURRENT。

## 后果与兼容

schema4 可在来源修订、Catalog 摘要、实体路径集合和总行数一致时迁移到 schema5；否则必须完整审计重建。索引文件是可重建派生物，Silver 与 Catalog 原件不因迁移改写。差集有文件数与字节预算，超限时故意退化为较慢的全量构建。此协议要求所有正式 Silver 写者提前推进修订；未登记的进程外文件改写仍须独立巡检，不能宣称跨进程原子快照。
